# AI-Assisted Development Policy: Claude Code and the Claude API

| | |
|---|---|
| **Applies to** | Everyone who uses Claude Code, the Claude API, or code generated by them in company repositories |
| **Owner** | Application Security (AppSec); changes via pull request with AppSec review |
| **Status** | Version 1.0 · effective on merge · reviewed every 6 months |
| **Setup guide** | [claude-guardrails-setup.md](claude-guardrails-setup.md) |

**Why this exists.** Claude is an approved tool, and we want you to use it. These rules let you use it for almost all work without asking anyone, and they keep the high-risk 5% safe. Most of them are enforced automatically, so you don't have to remember them. If a guardrail blocks legitimate work, tell us (see §7) instead of switching to an unapproved tool. Unapproved AI tools ("shadow AI") are not permitted for company code or data.

---

## 0. Risk tiers at a glance

| Tier | Typical work | Mode | Review |
|---|---|---|---|
| **0: General** | Questions, explanations, docs, boilerplate, tests, refactors with tests | Any approved mode, including auto | Normal PR review |
| **1: Product code** | Features and bug fixes in application code | Manual or accept-edits; auto inside the sandbox | Normal PR review; author must understand every line |
| **2: Critical** | Infrastructure-as-code, CI/CD, auth, crypto, access control, payment and data-retention logic, the guardrails themselves | Plan first, then Manual (supervised) | **Mandatory human review by a code owner (§3)** |

When in doubt, use the higher tier.

## 1. Execution controls

Claude Code's [permission modes](https://code.claude.com/docs/en/permission-modes) decide how much Claude can do without asking you. Cycle modes with `Shift+Tab`.

| Mode | What it does | Use it for | Allowed? |
|---|---|---|---|
| **Plan** | Reads and proposes, no edits | Starting any Tier 2 task; unfamiliar code | Yes, recommended |
| **Manual** (`default`, supervised) | Asks before each edit and non-allowlisted command | Tier 1 and Tier 2 work; **the repository default** | Yes |
| **Accept edits** | Auto-approves file edits in the workspace, still asks for commands | Tier 0–1 when you will review the diff before committing | Yes |
| **Auto** (autopilot) | A classifier approves routine actions; risky ones still prompt | Tier 0 tasks with tests, in the sandbox | Yes, Tier 0 only |
| **Bypass permissions** | Skips all prompts | Never on workstations | **Disabled by policy** |

Rules:

1. **You own every action Claude takes in your session**, and every line it writes that you commit.
2. Infrastructure is never changed from an agent shell. `terraform apply/destroy`, `kubectl delete`, `pulumi up`, package publishing and deploys are blocked. They run only through the reviewed CI pipeline.
3. Read every approval prompt before you approve it. "Yes, and don't ask again" is fine for commands you would run yourself. It is not fine for anything that deploys, deletes, pushes or reaches the network.
4. Unattended or headless runs (`claude -p`, CI agents) run only in ephemeral containers with no production credentials.

## 2. Data protection

**Never put any of these in a prompt, a pasted file, an MCP request, or a Claude API call:**

- **Credentials**: API keys, tokens, passwords, private keys, connection strings, session cookies, `.env` contents. *No exceptions.*
- **Personal data (PII)** of customers or employees: names linked to records, emails, phone numbers, government IDs (SSN/PESEL/NI), payment cards, IBANs, addresses.
- **Health data (PHI)**: anything identifying a patient or their care.
- **Production data**: database dumps, customer records, production logs that have not been scrubbed.
- **Third-party confidential material** you are not licensed to share.

**Fine to share:** this repository's code, synthetic or anonymised test data, scrubbed logs and stack traces, public documentation, architecture descriptions.

What the tooling does for you:

| Control | Behaviour |
|---|---|
| Prompt guard (Claude Code) | Blocks prompts that contain credentials (no override) and regulated PII. You get a redacted copy to resubmit. For synthetic data, add `[sensitive-ok: <reason>]`; the override is logged. Emails and phone numbers only trigger a reminder. |
| File and shell guards | Claude cannot read `.env`, keys, `~/.ssh`, `~/.aws`, cloud secret stores, or dump environment variables. |
| API safeguard | Apps calling the Claude API redact PII and credentials before the request leaves the process (§6). |

Detection is pattern-based. It **will** miss free-text personal data such as a patient's name and diagnosis written in prose. The rule above is what matters; the tooling is a safety net.

**If something slips through:** rotate the credential immediately, then report it to `#security-incidents` with the time and session ID. Reporting quickly is never penalised.

## 3. Code review: human in the loop (HITL)

All AI-assisted code goes through normal pull-request review. **Tier 2 changes additionally require approval from a code owner** in [`.github/CODEOWNERS`](../.github/CODEOWNERS):

| Area | Paths (examples) | Required reviewer |
|---|---|---|
| Infrastructure-as-code | `*.tf`, `*.tfvars`, `*.hcl`, `Dockerfile*`, `k8s/`, `helm/` | Platform Engineering |
| CI/CD | `.github/workflows/` | Platform Engineering + AppSec |
| Security-critical code | `auth/`, `security/`, `crypto/`, access-control and payment logic | AppSec |
| The guardrails | `.claude/`, `.mcp.json`, `CLAUDE.md`, `.pre-commit-config.yaml`, `scripts/claude_safeguard.py`, `config/claude-guardrails-policy.json`, `enterprise/` | AppSec |

For Tier 2 pull requests the author must:

1. Say in the PR description that AI assistance was used and for which parts. Keep the `Co-Authored-By: Claude` commit trailer that Claude Code adds.
2. Attach the `terraform plan` (or equivalent dry-run) output for IaC changes.
3. Explain the security impact in plain words: what new access, exposure or data flow the change creates.

Claude Code asks for explicit approval before editing these paths, even in accept-edits or auto mode. Pre-commit runs SAST (bandit, checkov) and secret scanning, and CI re-runs it all so `--no-verify` cannot skip it.

## 4. Tooling controls

### 4.1 Commands

| Category | Examples | Handling |
|---|---|---|
| Allowed without prompts | `git status/diff/log`, `npm run test/lint/build`, `pytest`, `ruff`, `mypy`, `terraform fmt -check/validate` | Runs immediately |
| Always ask a human | `git push`, `git reset/rebase`, dependency installs, `npx`, `docker`, `kubectl`, `helm`, cloud CLIs, `gh`, `rm`, `chmod`, `WebFetch` | Approval prompt in every mode |
| **Blocked** | `curl`, `wget`, `nc`, `ssh`/`scp`, other raw network clients; `sudo`; env dumps; secret-store reads; `git push --force`; `--no-verify`; `terraform apply/destroy`; `kubectl delete`; `npm publish`, `docker push`; privileged containers; pipe-to-shell of downloaded or decoded content | Denied with an explanation |

**Arbitrary network access from the agent shell is blocked outright.** Prompt injection in a README, issue or web page can turn a single `curl` into data exfiltration. Package managers and git can reach only the allowlisted registries through the sandbox. If Claude needs something from the internet, it will tell you what and why, and you fetch it.

The block is enforced in three layers: permission rules, a hook that parses the real command (catching `/usr/bin/curl`, `bash -c '…'`, `$(…)`), and the OS-level sandbox network allowlist.

### 4.2 Web access

- `WebSearch` is disabled.
- `WebFetch` requires approval for every request. Approve it only for documentation you would open yourself, and treat fetched content as untrusted.

### 4.3 MCP servers

Only internally hosted, AppSec-reviewed MCP servers over HTTPS are allowed. Organisation policy enforces this with an allowlist.

| Server | Purpose | Access | Auth |
|---|---|---|---|
| `internal-docs` | Search internal engineering docs | Read-only, no prompt | `INTERNAL_MCP_TOKEN` in your shell |
| `internal-tickets` | Read/update tickets | Every call asks for approval | OAuth via `/mcp` |

To add a server, open a PR that adds it to `.mcp.json`, `enabledMcpjsonServers` and the policy file. AppSec reviews its data access, its authentication, and whether its outputs could carry prompt injection. Local (stdio) MCP servers and public third-party servers are not allowed on workstations. Never put tokens in MCP config; use `${VAR}` references.

## 5. Logging and monitoring

| What | Where | Retention |
|---|---|---|
| Claude Code sessions: prompts, tool decisions, API usage and cost (OpenTelemetry) | Central collector → SIEM | Per security log policy (default 1 year) |
| Guardrail decisions (blocks, approvals, overrides): metadata only, no content | `.claude/audit/` on your machine | Until you delete it |
| Local transcripts | `~/.claude/projects/` | 14 days (`cleanupPeriodDays`) |
| Claude API app traffic (via `claude_safeguard`) | App stdout → SIEM | Per app logging policy |

Prompt text is logged centrally so that incidents can be investigated. It is visible only to the Security Operations team under the access-review process, and is never used for performance evaluation. That is another reason never to paste personal data.

## 6. Building applications with the Claude API

Services that send data to the Claude API must:

1. Call the API through `scripts/claude_safeguard.py` (or a reviewed equivalent) so prompts are redacted, every request emits an audit event, and responses are validated before use.
2. Load API keys from the secret manager at runtime. Never put them in code, config files, images or logs.
3. Treat model output as untrusted input. Never pipe it into a shell, `eval`, SQL or HTML without validation and encoding. Never auto-execute commands it proposes.
4. Pass the end user's identity (`user_id`) so audit events can be attributed.
5. Handle `stop_reason: "refusal"` and blocked or unsafe results gracefully in the UI.
6. Go through architecture review before handling personal, health or financial data, including data-residency and retention requirements.

## 7. Exceptions, false positives and incidents

- **False positive** (a guard blocks legitimate work): open an issue labelled `ai-guardrails` with the rule name from the message. Typical turnaround is 2 business days. Don't work around it with another tool.
- **Exception** (you need something this policy blocks): ask AppSec in `#appsec` with the use case, duration and data involved. Approved exceptions are time-boxed and recorded in `config/claude-guardrails-policy.json`.
- **Incident** (secret or personal data sent, suspicious agent behaviour, suspected prompt injection): rotate what's exposed, then report it in `#security-incidents`.

## Quick reference

**Do:** start Tier 2 work in Plan mode · use synthetic data · read approval prompts · review every AI diff as if a new teammate wrote it · report false positives.

**Don't:** paste secrets, customer data or production logs · approve network, deploy or push actions on autopilot · bypass hooks (`--no-verify`) · edit the guardrails without AppSec review · use unapproved AI tools for company work.
